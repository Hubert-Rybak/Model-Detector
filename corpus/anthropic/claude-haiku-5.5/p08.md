A hash table is a data structure that stores key-value pairs and finds them by key instead of by position. It works like this:

1. A **hash function** converts a key (a string, a number, etc.) into an integer.
2. That integer maps to a slot in an underlying array, usually by taking it modulo the array's size.
3. The key and value are stored in that slot. To look something up, you hash the key again and go straight to the slot without scanning anything.

Because you jump directly to the slot, lookups, inserts, and deletes take O(1) time on average. Two keys can land in the same slot (a collision), and implementations handle that by chaining entries in a small list per slot or by probing for the next empty one. When the table gets too full, it resizes and rehashes everything. An occasional insert is slow, but the cost averages out to constant time. Python's `dict` and `set`, Java's `HashMap`, and JavaScript's `Map` are all hash tables.

**How it compares to a list**

A list finds things by position. To find a value in an unsorted list, you have to check items one at a time.

| | List | Hash table |
|---|---|---|
| Find an item by value or key | O(n), scans until it finds a match | O(1) on average |
| Access by position | O(1) for array-backed lists | Not applicable |
| Range queries or sorted output | Natural if kept sorted | Not supported |
| Memory | Compact | Higher (spare slots and bookkeeping) |

**Reach for a hash table when:**

- You look things up by a key, like a user ID to a user record, or a setting name to its value.
- You need fast membership checks, like "have I seen this before?" for deduplication, visited sets in a graph search, or checking whether a URL was already crawled.
- You're counting or grouping, such as word frequencies or records bucketed by category.
- You're caching results so you don't recompute them.

**Stick with a list when:**

- Order or position matters, like the first three items or the most recent entry.
- You mostly loop over everything rather than searching for specific items.
- You need sorted output or range queries. A hash table can't answer "all values between 10 and 20" without checking every entry, but a sorted list with binary search, or a tree, can.
- The collection is small. A linear scan over a few dozen items is often just as fast, and a list uses less memory.
- You need duplicates kept in sequence, like a log of events.

**A quick example**

```python
# Each `in` check scans the whole list
allowed = ["alice", "bob", "carol"]   # imagine 100,000 names
if user in allowed:
    ...

# Each `in` check hashes the name and jumps straight to its slot
allowed = {"alice", "bob", "carol"}
if user in allowed:
    ...
```

A good rule of thumb: if you're writing `if x in some_list` inside a loop over another large collection, you probably want a set or dict instead.
