A **hash table** (also called a hash map, dictionary, or associative array) is a data structure that stores key → value pairs and lets you look up, insert, or delete by key in roughly constant time, O(1) on average, regardless of how many items it holds.

## How it works

1. A **hash function** turns the key into a number (e.g. `hash("alice") → 2847193`).
2. That number is mapped to a slot in an underlying array, typically `index = hash % array_size`.
3. The value is stored in that slot.
4. To find it later, you hash the key again and jump straight to that slot. No scanning.

Two details make it practical:

- **Collisions**: two keys can land in the same slot. Tables handle this either by keeping a small list per slot ("chaining") or by probing nearby slots for a free one ("open addressing"). As long as the hash function spreads keys evenly, each slot holds very few items.
- **Resizing**: when the table gets too full (the "load factor" rises), it rebuilds itself with a bigger array. That's an O(n) operation, but it happens rarely enough that inserts are still O(1) amortized.

In Python this is `dict` (and `set`, which is a hash table with keys only). In JavaScript it's `Map`/`Set` (and plain objects, more or less). Java has `HashMap`, Go has `map`, and so on.

## List vs. hash table

The key difference is *how you find things*:

| Operation | List | Hash table |
|---|---|---|
| Get item by position (`items[3]`) | O(1) | not supported |
| Find item by key/value | O(n), scan everything | O(1) average |
| "Is X in here?" | O(n) | O(1) |
| Insert at end | O(1) | O(1) |
| Keep items in a specific order | yes | no (Python dicts keep insertion order, but you can't sort in place or index into them) |
| Memory | compact | more overhead (empty slots, hash storage) |

## When to reach for a hash table

- **You look things up by identity, not position.** "What's the price for SKU 4471?" "Does this username exist?" With a list you'd scan; with a dict you jump.
- **Membership checks inside a loop.** This is the classic trap:
  ```python
  # O(n * m): for each item, scan the whole list
  for item in items:
      if item in allowed_list:
          ...

  # O(n): set lookup is constant time
  allowed = set(allowed_list)
  for item in items:
      if item in allowed:
          ...
  ```
  With 10,000 items on each side that's the difference between 100 million comparisons and 10,000.
- **Counting, grouping, deduplicating.** `counts[word] += 1`, `by_category[cat].append(x)`, `seen.add(id)`.
- **Caching / memoization.** Map input → previously computed result.
- **Joining two datasets** by a shared key, like a database join in memory.

## When a list is still the right choice

- **Order or position matters**: a queue of tasks, lines in a file, a sequence of events, "give me the 5th one."
- **You iterate over everything anyway** and never search. A hash table buys you nothing there.
- **Small collections.** For a handful of items (say, under 10 to 20), a linear scan through a list is often faster than hashing, because the constant factors are tiny and the data fits in cache. Don't over-engineer.
- **You need sorted order or range queries** ("everything between 10 and 50"). Hash tables can't do that; you want a sorted list, a tree, or a database index.
- **Keys aren't hashable.** Keys need to be immutable (strings, numbers, tuples). You can't key a dict by a list or another dict without converting it first.

## Rule of thumb

If you ever write `if x in some_list` inside a loop, or `next(item for item in items if item.id == target)`, that's the signal. You're using a list as a lookup structure, and a dict or set will almost certainly be the better tool.
