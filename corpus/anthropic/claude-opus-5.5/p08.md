A **hash table** stores data as key → value pairs and lets you find any value by its key in roughly constant time, no matter how much data it holds.

### How it works

Under the hood, a hash table is an array of slots, often called buckets. To store `"alice" → 30`:

1. A **hash function** turns the key `"alice"` into a large integer.
2. That integer is mapped to a slot index, for example `hash("alice") % number_of_slots`.
3. The pair is stored in that slot.

To look up `"alice"` later, the table hashes it again and goes straight to that slot without searching. Sometimes two keys land in the same slot, which is called a **collision**. The table then either keeps a short list in that slot or looks for another empty one. It also grows and spreads its entries out as it fills up, so collisions stay rare.

As a result, lookup, insert and delete are **O(1) on average**. A list is fast when you access by *position* (`items[2]`). Finding a particular *value* in a list, though, means checking the elements one by one, which is **O(n)**.

You've probably used hash tables already: Python's `dict` and `set`, JavaScript's `Map` and `Set`, Java's `HashMap`, C#'s `Dictionary`, C++'s `unordered_map` and Go's `map`.

```python
# List: scan until we find "bob"
users = [("alice", 30), ("bob", 25), ("carol", 35)]
for name, age in users:
    if name == "bob":
        print(age)
        break

# Hash table: jump straight to "bob"
users = {"alice": 30, "bob": 25, "carol": 35}
print(users["bob"])
```

With three users there's no real difference. With a million, the list may have to check a million entries to find one, while the dict goes straight to it.

### Use a hash table when you need to…

- **Look things up by a key**: users by ID, products by SKU, settings by name.
- **Check "have I seen this?" many times**: use a set.
- **Remove duplicates**: `set(items)`.
- **Count or group things**: word frequencies, orders per customer.
- **Match up two collections**: put one in a dict or set and look up from the other instead of using a nested loop. That turns O(n × m) into O(n + m).
- **Cache results**: memoization is just a hash table that maps inputs to outputs.

The most common real-world case is checking membership inside a loop:

```python
banned = load_banned_ids()   # a list of 100,000 IDs
for user in users:           # 1,000,000 users
    if user.id in banned:    # scans the whole list every time
        ...
```

That's up to 100 billion comparisons. If you change the first line to `banned = set(load_banned_ids())`, it becomes about a million constant-time lookups. The loop stays the same and only one line changes.

### Stick with a list when you…

- **Care about position or order**: "the 3rd item," "the last 10 entries," a queue of tasks.
- **Want to keep duplicates**: a log of every purchase, repeats included.
- **Mostly go through every item**: if you never look items up, a hash table only adds overhead.
- **Need sorted order or ranges**: "all scores between 80 and 90." Hashing scatters keys on purpose, so use a sorted list with binary search or a tree-based map instead.
- **Have a small collection**: scanning ten items costs almost nothing, and a list is simpler.

### Caveats

- **Keys must be hashable.** In Python, strings, numbers and tuples work as keys, but lists and dicts don't.
- **O(1) is the average case.** With lots of collisions, from a poor hash function or deliberately crafted input, it can slow toward O(n). Standard library versions guard against this well.
- **They use more memory** than a list of the same items, because they keep empty slots around to stay fast.

**Rule of thumb:** if you keep searching a list for "the item whose X is Y," build a hash table keyed by X. If what matters is order (first, next, last), use a list.
