A hash table is a structure that lets you look things up by a key in roughly constant time, no matter how many items it holds.

**How it works.** You give it a key (a string, a number, a tuple). It runs the key through a hash function, which turns it into a number, and uses that number to pick a slot in an internal array. The value goes in that slot. Lookup does the same computation and jumps straight to the slot. Two keys sometimes land in the same slot (a collision); the table handles that by chaining the entries or probing nearby slots, and it grows the array when it gets crowded so collisions stay rare. In Python this is `dict` and `set`; in JavaScript it's `Map`, `Set`, and plain objects.

**When to use it instead of a list:**

- You look things up by identity, not by position. "What's the price of item X?" is a hash table question. "What's the third item?" is a list question.
- You need membership tests often. `x in my_set` is O(1); `x in my_list` scans the whole list.
- You're counting or grouping. A dictionary from key to count or key to list is the natural shape.
- You need to deduplicate.

**When a list is still better:**

- Order matters and you iterate in sequence.
- The collection is tiny (a few items), where the hash overhead isn't worth it.
- You need sorted traversal or range queries; that's a sorted array or a tree.
- Keys aren't hashable (mutable lists as keys, for example).

Rule of thumb: if you ever find yourself writing a loop whose only job is to find an item by some key, you want a hash table.
