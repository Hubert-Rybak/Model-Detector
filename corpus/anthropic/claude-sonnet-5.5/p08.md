A **hash table** is a data structure that stores **key → value** pairs. It lets you find, add, or remove an entry in roughly constant time, however many entries there are. You've probably already used one: Python's `dict` and `set`, JavaScript's `Map` and `Set`, Java's `HashMap`, and Go's `map` are all hash tables.

## How it works

1. Under the hood there's an array of "buckets."
2. When you insert a key, a **hash function** turns it into an integer. That integer (modulo the array size) picks a bucket.
3. The key and value are stored in that bucket.
4. To look something up, you hash the key again, jump straight to the same bucket, and read the value. Nothing else gets searched.

Sometimes two keys land in the same bucket (a **collision**). Implementations handle that by keeping a tiny list in each bucket or by probing for the next free slot. When the table gets too full, it resizes itself (usually doubling) and re-inserts everything so the buckets stay short. That's why operations are O(1) *on average*, with an occasional insert costing more when a resize happens.

## Hash table vs. list

| Operation | List / array | Hash table |
|---|---|---|
| Get item by position (`items[3]`) | O(1) | not applicable |
| Find by value / check membership | O(n), scans the list | O(1) average |
| Insert | O(1) at the end, O(n) elsewhere | O(1) average |
| Delete | O(n) (elements shift) | O(1) average |
| Keeps a meaningful order | yes | depends on language |

## Reach for a hash table when...

- **You look things up by something other than position.** Examples are user ID → user, word → count, and filename → contents.
- **You do lots of "have I seen this?" checks.** Swapping a list for a `set` here is one of the easiest big performance wins.
- **You're counting, grouping, or deduplicating.** That covers word frequencies, bucketing records by category, and removing repeats.
- **You're matching up two collections.** Joining two datasets on an ID or solving "find two numbers that sum to a target" are typical cases.
- **You want a cache.** It maps an input to a previously computed result.

```python
# List: every `in` check scans the whole list -> O(n * m) overall
banned = ["alice", "bob", "carol"]  # imagine 100,000 names
allowed = [u for u in users if u not in banned]

# Set (a hash table): each check is O(1) -> O(n + m) overall
banned = {"alice", "bob", "carol"}
allowed = [u for u in users if u not in banned]
```

The code is nearly identical, but the second version stays fast as the data grows.

## Stick with a list when...

- **Order or position is the point.** You access items by index or iterate in sequence.
- **The collection is small.** With a handful of items, a linear scan is just as fast, and often faster because of cache locality and no hashing cost.
- **You need sorted data or range queries.** "Everything between 10 and 20" doesn't work on a hash table, because keys are scattered by design. Use a sorted array or a tree-based structure instead.
- **Duplicates matter.** Keys in a hash table are unique.
- **Your items can't be good keys.** Keys need to be hashable and effectively immutable. In Python, for example, you can't use a list as a dict key.
- **Memory is tight.** Hash tables carry overhead for empty buckets and bookkeeping.

## Caveats

- O(1) is the *average* case. If lots of keys collide (a poor hash function, or deliberately adversarial input), lookups can degrade toward O(n). Mainstream libraries take steps to guard against this, so you'll rarely run into it.
- Iteration order varies by language. Python dicts and JavaScript Maps keep insertion order, Go deliberately randomizes it, and Java's `HashMap` makes no promises (use `LinkedHashMap` if you want order).

**Rule of thumb:** if you keep searching a list, whether with `x in my_list` inside a loop or by looping to find the item with a matching ID, that's usually a sign you want a hash table instead.
